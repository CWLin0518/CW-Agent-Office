實測時發現一個執行期錯誤（非 code review 抓到，是真人操作觸發的）：`handlePortPointerMove` 在 `setWireDrag` 的 updater function 裡才讀 `event.currentTarget`，但 React 合成事件的 `currentTarget` 在 handler 同步執行完就會變成 null（符合原生 DOM 事件規範），updater 卻是延後到 state 更新處理時才呼叫——拖曳端點移動滑鼠時就會噴 `Cannot read properties of null (reading 'getBoundingClientRect')`。已修成在 handler 內同步算好座標，updater 只單純合併，不再碰 `event`。

使用者後續回報畫布上的藍色虛線（derived 連線）想要能清除，補了兩個功能：① derived 連線右鍵「清除這筆記錄」，呼叫新的 `agent_canvas_delete_derived_link`（`delete_derived_link` 是方向性刪除，不像 authored 是無方向——因為 a→b 和 b→a 是各自獨立的往來事實，不是同一組關係）；之後如果這兩個 Agent 又真的有 gto send，線會自動重新出現，這只是清畫面顯示，不影響 gto send 權限。② 畫布控制列新增顯示/隱藏 derived 連線的切換鈕（純前端渲染過濾，不動資料庫）。

後端 `local_bridge.rs` 的 edge 授權邏輯與 `agent_create_with_repo` 的 parent 政策檢查因既有測試套件（roles/departments 子系統殘留的大量已損壞測試檔，與本階段無關）目前無法整體 `cargo test`，新增測試已個別確認可編譯但無法實際執行；真人操作驗證（端點拖拉建線／Shift 取消連接／端點右鍵取消連接／derived 連線清除與顯示切換／未連線時 gto send 應被拒絕）尚未完整跑過，需要有人在桌面 App 裡再驗一輪。

7 項決策已定案 2026-08-22
1 第 1 節連線語意
✓ 兩者都要（authored + derived）
落地方式：derived 先在 P4 做，authored 排到 P4.5。derived 連線資料來源既有、風險低；authored 連線牽涉存取控制與使用者互動設計。
2 第 2 節外部路徑是否跨機器同步
✓ 不用，本機路徑就好
外部 Agent 路徑只需支援本機檔案系統路徑，不做跨機器同步或雲端功能。簡化設計範圍，現階段不支援分散式共享。
3 第 3 節 17 類權限 Phase B 優先度
✓ 不急，按順序開發
Phase B（Network / Tool / Database / Secrets 等）不需要為特定類別插隊。按文件裡判斷的順序開發即可。Phase A 五類優先實裝。
4 與 PRD 對齊（Runtime Snapshot/Lifecycle State）
✓ 採方案 (a)，P0 先對齊
P4（agent-canvas）動工前，P0 階段先花一輪對照 `AGENT_RUNTIME_UPGRADE_PRD.md` 的 Runtime Snapshot/Lifecycle State 雛形。結論記錄下來再動工，不刻意繞開。
5 第 2 節 Agent Definition/Instance 雙層架構
✓ 不做，採較小方案
v1 在 `AgentProfile` 加 `external_template_path` 欄位即可。不做正式的雙層架構。之後如果發現需要範本版本管理、多專案分享等需求，再另外評估演化。
6 第 5 節外部 Provider 防護程度
✓ v1 做版本鎖，簽名先留白
v1 就做版本鎖（content hash 比對 + 檔案有變時強制 preview/confirm）。完整簽章驗證因需先決定金鑰/信任模型，schema 先保留欄位，不在 v1 做驗證邏輯。
7 第 2 節跨 Workspace 執行位置
✓ 不存在跨 workspace 執行
Agent 一律在使用者目前所在的 workspace 內建立與執行。不新建承接用的 workspace，也不需要 local bridge 做跨 workspace 轉發。「我在哪個專案的介面，Agent 就在那個介面」。
