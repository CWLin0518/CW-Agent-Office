# 04 客製化設計：GT Office 改版規劃

> 這份文件記錄「你想怎麼改」，是設計文件，不是現狀 SPEC。現狀請看 [01_前端架構.md](01_前端架構.md)、[02_後端架構.md](02_後端架構.md)、[03_前後端通訊與多Agent協作機制.md](03_前後端通訊與多Agent協作機制.md)。這份文件會大量引用那三份文件的結論，看不懂的名詞可以回去查。
>
> 狀態：設計已定案（2026-08-22，見第 9 節），尚未開發。每個章節都會標明「現況地基」（已經有什麼可以用）和「設計」（要新增/改什麼），並在文末給出分階段路線圖。第 9 節的 7 項決策已同步反映進第 1-8 節內文，動工前不需要再回頭確認這些點。

## 0. 需求總覽

1. 一個節點串接式（Grasshopper 風格）的 Agent 協作畫布，節點是 Agent，連線表示溝通關係，可在畫布上建立 subagent
2. Agent 改版：可存放在專案外的指定路徑，讓專案內的 Agent 呼叫外部的 multi-agent 系統
3. 新增 Agent 時要有「權限」分頁，涵蓋檔案系統、Shell、網路、工具/MCP、資料庫、密鑰、Git、Agent、模型、預算、執行、套件、基礎設施、認證、對外行為、日誌/記憶、人工核准、政策/安全共 17 大類
4. 每個終端機介面都要有「開啟 new session」按鈕
5. 設計時要為未來加入更多 LLM CLI（不只 Claude Code / Codex）預留相容性
6. 終端機渲染破圖要修；未來要做遊戲化「辦公室」首頁，每個專案是一間辦公室，Agent 是員工，可觀察運作狀態

以下每節先講「現況地基」（這個需求在現有程式碼裡已經有什麼可以站），再講設計方向。**沒有一節是從零開始**——GT Office 現有架構對這六個需求都已經有部分基礎或明確的相似先例，設計時優先延伸既有模式，而不是另起一套。

## 1. Agent 協作畫布（節點式 Canvas）

### 現況地基

GT Office 已經有一套節點圖畫布的先例：`business-designer` feature。

- `apps/desktop-web/src/features/business-designer/components/DesignerGraphCanvas.tsx` — 現成的圖形畫布元件
- `apps/desktop-web/src/features/business-designer/model/designer-blocks.ts`、`designer-graph.ts` — 節點（Block）與連線（Link）的資料模型
- `CONTEXT.md` 定義了這套詞彙：**Block**（圖上的節點）、**Link**（節點間的推導關係）、**Derived Link**（連線的語意是從內容算出來的，不是使用者手畫的連接器）

這套東西是為「需求設計」這個領域做的（Block 是需求結構單元），**不能直接拿來裝 Agent**——但畫布渲染、拖拉、縮放、Inspector 側欄（`DesignerInspector.tsx`）這些「畫布本身怎麼運作」的工程解法可以參考、甚至抽出共用邏輯，只是節點/連線的**資料模型必須是全新的**，屬於 Agent 協作領域，不是 Business Designer 領域。混用會違反 `CLAUDE.md` 的「不要用便利導入破壞模組邊界」規則。

另外，多 Agent 協作目前走的是 `gto` 協議（見 03 章第 2 節）：Station A 執行 `gto send A B "..."`，經 local bridge 寫進 Station B 的 inbox。這代表**「誰跟誰講過話」這個資料其實已經存在**（`crates/gt-task` 的任務派發紀錄），只是現在沒有畫成圖。

### 設計

新增一個 feature：`apps/desktop-web/src/features/agent-canvas/`，後端對應 `apps/desktop-tauri/src-tauri/src/commands/agent_canvas/`（遵守 01 章第 4 節「feature 與 commands 一比一對齊」的規則）。

**節點（Node）** = 一個 Agent（對應現有 `AgentProfile`，見 `crates/gt-agent/src/models.rs`）。節點要能顯示即時狀態。

> ⚠️ **決策已定案（2026-08-22，見第 9 節決策 4：採方案 a）：不要急著接 `station-agent-runtime-model.ts` / `useStationActivitySignal.ts`，P3 動工前要先花一輪對照 `docs/AGENT_RUNTIME_UPGRADE_PRD.md`（03 章第 5 節點名要先讀的那份 PRD）。** 這份 PRD 開宗明義就是要解決「Agent 運行狀態分散在 Station 卡片狀態、終端進程探測、Provider session…」這個問題，並提案一個統一的 `Agent Runtime Contract`（`Runtime Snapshot` / `Lifecycle State` / `Attention Projection`）——這兩個檔案很可能正是 PRD 想歸併掉的分散狀態來源之一。**P0 資料模型地基階段要把這輪對照納入範圍**：agent-canvas 節點狀態要嘛直接借用 PRD 的 `Runtime Snapshot`/`Lifecycle State` 雛形，要嘛明確設計成跟畫面無關的通用資料層（呼應第 6.2 節、第 8 節 P3 驗收標準），總之不能做完 P3 之後才發現要整套重寫。

**連線（Edge）** 需要先決定語意，這是一個產品決策，不是純技術問題：

- **手畫連線（Authored）**：使用者在畫布上拉線，宣告「這兩個 Agent 允許互相溝通」。後端要真的拿這條線去做存取控制（local bridge 收到 `gto send` 時檢查來源/目的 Agent 之間是否存在一條 authored edge），否則畫布只是裝飾。
- **推導連線（Derived）**：比照 Business Designer 的 Derived Link 精神，畫布另外疊一層「最近實際有 `gto send` 往來」的連線，用顏色/動畫跟 authored 連線區分，資料來源是 `crates/gt-task` 既有的派發紀錄，不需要使用者手動維護。

**決策已定案（2026-08-22，見第 9 節決策 1）：兩者都要**。分階段落地：derived 連線資料來源既有、風險低，先在 P3 MVP 做；authored 連線牽涉存取控制、需要使用者互動設計，排在 P3.5（見第 8 節路線圖，順序不變）。要注意：一旦 authored 上線且真的拿去做存取控制，會讓「Agent 之間本來就能透過 `gto` 互相 send，沒有邊界檢查」的現況出現行為變化（等於新增一道之前沒有的限制）——這是預期中的定案結果，不是需要再確認的疑慮，但實作 P3.5 時要在變更說明/UI 裡讓使用者清楚知道這件事發生了。

**在畫布上建立 subagent**：目前 `AgentProfile` 沒有父子關係欄位，`AgentScope` 只有 `Station` / `Designer` 兩種。需要新增：

- `crates/gt-agent/src/models.rs`：`AgentProfile` 增加 `parent_agent_id: Option<String>`
- `crates/gt-storage/src/agent_repository.rs`：對應的 schema migration。**注意**：檔案第 69-86 行那段整表重建（`CREATE TABLE ... without_roles` → `DROP` → `RENAME`）是「移除舊欄位」情境的寫法，不適合拿來當「新增一個可空欄位」的範例，照抄會做出不必要的複雜度。新增可空欄位請比照 `crates/gt-storage/src/ai_config_repository.rs:132` 的 `ALTER TABLE ... ADD COLUMN settings_json TEXT` 寫法即可
- 畫布上對節點按右鍵「新增 subagent」時，新節點的 `parent_agent_id` 指向被點的節點，畫布上自動畫一條表示「隸屬關係」的連線（跟溝通關係的 Edge 要視覺區分開，語意不同：一個是「誰管誰」，一個是「誰跟誰說話」）

**涉及檔案（新增/擴充）**：
- 新增 `apps/desktop-web/src/features/agent-canvas/`（元件、model、controllers，比照 `business-designer` 的資料夾分工）
- 新增 `apps/desktop-tauri/src-tauri/src/commands/agent_canvas/`
- 擴充 `crates/gt-agent`（parent_agent_id）
- 新增連線儲存：`crates/gt-storage` 新表 `agent_links`（id, workspace_id, from_agent_id, to_agent_id, kind[authored|derived], created_at_ms）

## 2. Agent 外部存放路徑 + 跨專案呼叫外部 multi-agent 系統

### 現況地基

這個需求會直接踩到 GT Office 現有一條**刻意設計的安全邊界**：`workspace_id` 是硬邊界（03 章第 1 節）。`gt-security`、`gt-filesystem` 強制所有檔案/終端機操作不能跑出 workspace 根目錄；`CLAUDE.md` 明文寫「多工作區操作必須顯式攜帶 workspace_id」「自訂 cwd 必須位於 workspace 內」。目前 `AgentProfile` 也是 `workspace_id` 外鍵，一個 Agent 天生綁死一個 workspace。

所以「Agent 存放在專案外」不能簡單理解成「把資料庫路徑改到別的地方」——但**決策已定案（2026-08-22，見第 9 節決策 5、7）：v1 不做雙層架構，用最小改動達成效果，且執行行為完全不跨 workspace**。以下是定案後的設計。

### 設計

**不新增 Agent Definition / Agent Instance 兩層概念**，只在 `AgentProfile` 上加一個欄位：

```rust
pub struct AgentProfile {
    // ...現有欄位
    pub external_template_path: Option<String>,
}
```

建立 Agent 時，使用者可以選擇「從這個外部路徑（本機檔案系統路徑，不做跨機器同步，見決策 2）讀取 prompt / policy 模板」。讀到的內容 materialize 進這個 workspace 的 prompt 檔（`CLAUDE.md`/`AGENTS.md`，沿用 `crates/gt-agent/src/models.rs` 的 `prompt_file_name_for_tool`），之後這個 Agent 的行為、執行、資料儲存都跟現在完全一樣——**只是初始設定的來源可以指向專案外的一個路徑**，沒有新的資料層、沒有新 crate、`workspace_id` 邊界完全不受影響。這個欄位只是「建立時從哪裡讀初始內容」的來源標記，之後要不要再從外部路徑重新同步/更新內容，是後續才需要決定的細節，v1 先做「建立時讀取一次」就好。

**「讓專案內的 Agent 呼叫外部存放的 multi-agent 系統」的重新定義（決策 7 之後）**：使用者的決策是「我在哪個專案的介面，Agent 就應該在那個介面」——也就是**不存在真正意義上的「跨 workspace 執行」**。所以這句需求在拍板後的實作意義是：使用者在目前這個專案（workspace）裡，用上面的 `external_template_path` 建立一個「從外部範本套用」的 Agent，這個新 Agent 就是這個 workspace 裡一個普通的 `AgentProfile`，透過現有 `gto` 協議（03 章第 2 節）跟同一個 workspace 內的其他 Agent 溝通——**跟現有機制完全一致，不需要 local bridge 新增任何跨 workspace 轉發邏輯**。這個決策同時也解掉了原本卡住 implementer 的「該落在哪個 workspace」問題：答案就是使用者目前所在的那個 workspace，沒有例外。

> 這個決策讓第 2 節的範圍大幅縮小：不需要新 crate、不需要 local bridge 改動、不需要處理跨 workspace 的協作邊界問題。如果之後實際使用後發現「呼叫外部系統」還有更複雜的需求（例如真的要連到一個獨立運行、不在任何 GT Office workspace 裡的外部 multi-agent 服務），屆時再重新開一輪設計討論，不在這次範圍內預先設計。

**涉及檔案（新增/擴充）**：
- `crates/gt-agent/src/models.rs`：`AgentProfile` 新增 `external_template_path: Option<String>`
- `crates/gt-storage/src/agent_repository.rs`：對應的 `ADD COLUMN` migration（比照第 1 節提到的 `ai_config_repository.rs:132` 寫法）
- Agent 建立流程 UI（`StationManageModal.tsx`）新增「從外部路徑套用範本」的選項，讀取本機檔案系統路徑
- 對應 `apps/desktop-tauri/src-tauri/src/commands/agent/` 新增讀取外部範本內容的 command（純檔案讀取，仍要走 `gt-security` 的路徑驗證，但這裡驗證的是「外部路徑本身存在且可讀」，不是 workspace 邊界檢查）

## 3. 新增 Agent 的「權限」分頁

### 現況地基

`AgentProfile`（`crates/gt-agent/src/models.rs`）其實已經有一個 `policy_snapshot_id: Option<String>` 欄位，資料庫 schema 也有這一欄（`crates/gt-storage/src/agent_repository.rs`）——但目前**建立 Agent 時永遠寫入 NULL**（第 189 行 `INSERT ... VALUES (..., NULL, ...)`），從來沒有真正被賦值或讀取過。這是一個已經預留、但從未落地的欄位，剛好是這個需求的掛勾點。

權限的「執行面」現況：`gt-abstractions` 定義了 `CommandPolicyEvaluator` trait，目前只有一個方法：

```rust
pub trait CommandPolicyEvaluator: Send + Sync {
    fn can_access_path(&self, workspace_id: &WorkspaceId, path: &Path) -> bool;
}
```

而唯一的實作是 `AllowAllPolicyEvaluator`（見 `gt-abstractions/src/lib.rs` 454-458 行）——**目前實質上沒有任何權限限制**，這個 trait 只是路徑檢查的介面，全部放行。這代表你要的 17 類權限，現有程式碼只覆蓋了「檔案路徑」這一小塊，而且還沒真的擋任何東西。

### 設計

**資料模型**：新增 `AgentPolicy`，用 `policy_snapshot_id` 指向一份不可變的快照（比照 `gt-ai-config` 現有的 `preview -> validate -> confirm -> apply -> audit` 流程精神，`CLAUDE.md` 明文要求 AI 設定變更走這個流程），存在新表 `agent_policy_snapshots`（id, workspace_id, agent_id, policy_json, created_at_ms）。每次修改權限產生一份新快照，不覆蓋舊的，方便之後稽核「這個 Agent 在做某件事的當下，權限設定是什麼」。

**17 類權限不要一次全做**，這是我要提醒的地方：你列的表格裡有些類別現有系統完全沒有對應的執行機制（例如 Infrastructure 的 Deploy/Restart——GT Office 本來就不做部署這件事；Budget 的 Token Budget——現有 `gt-ai-config`/`gt-task` 沒有任何 token 計量），做成 UI 上的開關但後端不執行，會變成「假權限」，比不做還危險（使用者以為擋住了，其實沒擋）。建議分兩批：

**Phase A（有現成掛勾點，可以真的執行）**：
| 類別 | 掛勾到哪裡 |
|---|---|
| File System | `CommandPolicyEvaluator::can_access_path`（已存在，只是目前全放行）+ `gt-filesystem` |
| Shell / Terminal | `gt-terminal` 建立 session 時的指令白名單/黑名單檢查（`PtyTerminalProvider::create_session`） |
| Git / VCS | `crates/gt-git` 執行指令前檢查 |
| Agent（Invoke/Spawn/Delegate） | `local_bridge.rs` 的 `gto send`/建立 subagent 邏輯——**v1 先做成「這個 Agent 是否允許呼叫 `gto send` / 建立 subagent」的單純開關，不依賴 authored edge**，因為 authored edge 要等第 1 節的 P3.5 才存在（見第 8 節路線圖）。之後 P3.5 做完可以再把這條規則升級成「依 edge 授權」，但 v1 不能寫成依賴一個還不存在的機制，否則這一類在 Phase A 階段其實是假權限 |
| Execution（Timeout/Max Steps/Concurrency） | `gt-task` 任務派發時套用 |

**Phase B（需要先新建對應子系統，才有東西可以掛）**：Network、Tool/MCP、Database、Secrets、Model/LLM、Budget、Package、Infrastructure、Authentication、External Actions、Logging/Memory、Human Approval。這些要嘛現有系統還沒有對應的攔截點（例如 Network——PTY 裡跑的程式要連外網，現在完全沒有攔截層），要嘛需要新的 UI 流程。**優先順序決策已定案（2026-08-22，見第 9 節決策 3）：Phase B 不急，就照這裡列的順序開發，不需要為特定類別插隊。**

> **Human Approval 特別說明**：不要把這類當成一個要從零設計的中斷機制去想。`docs/AGENT_RUNTIME_UPGRADE_PRD.md` 已經定義了語意幾乎重疊的 `blocked` Lifecycle State（「Agent 顯式要求權限、確認、關鍵決策或無法繼續的輸入」）以及對應的 Status Authority／Explain 機制。決策 4 已定案要先對齊 PRD，所以 Human Approval 應該直接建在 P0 對齊出來的 `blocked` 狀態之上，而不是另開一套獨立的中斷機制。

「Policy / Security」（Allow/Deny/Require Approval/Sandbox/Escalation）不是獨立一類權限，它是**套用在其他每一類權限上的執行模式**，設計上應該做成每條規則的「動作」欄位，而不是第 18 個分類。

**前端 UI**：現有的 Agent 建立/管理入口是 `apps/desktop-web/src/features/workspace-hub/StationManageModal.tsx`，在裡面加一個「權限」分頁（tab），Phase A 五類先做成可勾選/可填 allowlist 的表單，Phase B 類別可以先做成 UI 佔位（顯示但標註「即將支援」），避免做出「勾了沒用」的假象。

**涉及檔案**：`crates/gt-agent`（新增 policy 模組）、`crates/gt-abstractions`（擴充 `CommandPolicyEvaluator` 或新增對應的 evaluator trait）、`crates/gt-storage`（`agent_policy_snapshots` 表）、`StationManageModal.tsx`、對應 `apps/desktop-tauri/src-tauri/src/commands/agent/`。

## 4. 終端機介面的「New Session」按鈕

### 現況地基

這是六個需求裡地基最完整的一個。後端 `gt-terminal` 的 `sessions` 本來就是 `HashMap<String, ...>`，一個 workspace 可以同時存在多個 PTY session，不是寫死一對一；`features/session` 已經有「Agent 對話 session 的歷史列表、恢復對話」的機制。前端終端機渲染在 `apps/desktop-web/src/features/terminal/StationXtermTerminal.tsx`，掛載終端機的容器是 `apps/desktop-web/src/features/workspace-hub/TerminalStationPane.tsx`（Station 卡片內）和 `DetachedWorkbenchWindow.tsx`（分離視窗）。

也就是說：**能開多個 session 這件事後端早就支援，純粹是前端沒有一個按鈕去觸發它、也沒有 UI 去切換/管理已經開的多個 session**。

### 設計

在 `features/terminal` 底下做一個共用的「session 分頁列（tab bar）」元件（例如 `SessionTabBar.tsx` + `session-tab-model.ts`），提供：新增 session（呼叫既有的建立 session command，見 03 章）、切換使用中 session、關閉 session。

**放在 `features/terminal` 而不是各自塞進 `TerminalStationPane.tsx`**：因為未來至少有三個地方要用到「一個終端機容器要能開多個 session」——Station 卡片、分離視窗、第 1 節的 agent-canvas 節點內建終端機。三個地方各自寫一份會違反 `CLAUDE.md`「不要用便利導入破壞模組邊界」，也會讓行為不一致（例如關閉最後一個 session 時該怎麼處理，三份實作可能各寫各的）。共用元件做好之後，`TerminalStationPane.tsx`、`DetachedWorkbenchWindow.tsx` 只需要組合它。

**涉及檔案**：新增 `apps/desktop-web/src/features/terminal/SessionTabBar.tsx` + 對應 model；修改 `TerminalStationPane.tsx`、`DetachedWorkbenchWindow.tsx` 接上這個共用元件。這節不太需要動後端（建立 session 的 command 已存在），是六節裡少數「單純前端工作」的一節。

## 5. 為未來更多 LLM CLI 預留相容性

### 現況地基

這是這次盤點裡發現**現況跟目標差距最大**的一節，值得特別說明。

`crates/gt-tools/src/agent_installer.rs`（一支超過 2000 行的檔案）目前的 provider 定義方式是寫死的 enum：

```rust
pub enum AgentType {
    ClaudeCode,
    Codex,
}
```

偵測、安裝、解除安裝、npm 套件名稱（`@anthropic-ai/claude-code` / `@openai/codex`）、Homebrew cask 名稱、官方安裝腳本 URL……全部是對這個兩選一的 enum 寫 `match` 分支硬編碼。`crates/gt-agent/src/models.rs` 的 `normalize_tool_provider_key` 也一樣：只認得字串裡有沒有包含 `"claude"`，其他一律當成 `"codex"` 處理（也就是說目前如果你手動加一個第三種 CLI，它的 prompt 檔名會被誤判成 `AGENTS.md`）。

**這不是危言聳聽的技術債，是這個需求要優先處理的東西**：不重構這一層，之後每加一個新 LLM CLI（Gemini CLI、Aider…）都要在這支 2000 行檔案裡新增好幾處 `match` 分支，違反「新增依賴/能力前，先確認方案」的專案原則，也很容易漏改某一處（例如漏掉 uninstall 邏輯）。

值得一提的好消息：安裝流程本身已經是「一串 attempt 清單」的資料結構（`AgentInstallAttempt` / `AgentInstallPlan`），不是寫死的指令式流程——這部分的**形狀**已經是對的，只是清單內容目前由 `match agent { ClaudeCode, Codex }` 產生，要做的是把「產生清單」這一步改成從資料驅動的 Provider 描述讀取，而不是重寫整個安裝機制。

### 設計

新增 **Provider Descriptor**：一個描述「什麼是一個 LLM CLI provider」的資料結構，取代現有的兩選一 enum：

```rust
pub struct AgentProviderDescriptor {
    pub id: String,                    // "claude" / "codex" / "gemini-cli" ...
    pub display_name: String,
    pub executable_name: String,
    pub prompt_file_name: String,      // CLAUDE.md / AGENTS.md / ...
    pub install_methods: Vec<InstallMethod>,  // npm package / brew cask / official script
    pub supports_gto: bool,            // 是否原生支援 gto 協議
    pub supports_mcp: bool,
}
```

分兩層來源：
1. **內建 Provider**：Claude Code、Codex 現在的行為原封不動遷移過來，作為程式碼內建的兩份 Descriptor，行為零變化，只是資料來源從 `match` 改成查表。
2. **外部 Provider（可擴充）**：從使用者指定的本機路徑（例如 `~/.gtoffice/providers/*.toml`，在 Settings 裡設定，獨立於第 2 節的單一 Agent `external_template_path` 欄位——第 2 節定案後已經不是「一個共用的 Agent Library 目錄」概念，這裡的 Provider Descriptor 目錄是它自己獨立的設定項）載入使用者/社群自訂的 Provider 描述。這樣要支援一個新 LLM CLI，不需要等 GT Office 出新版本，使用者自己寫一份描述檔就能加進來。

> 🔒 **這一步是這份文件裡風險最高的設計，比第 3 節反覆強調要避免的「假權限」更嚴重——這是一份外部、可編輯的檔案，內容會被拿去執行安裝腳本（`install_methods` 裡包含官方安裝腳本 URL）。** 這正好是 `docs/AGENT_RUNTIME_UPGRADE_PRD.md` 風險表已經點名的「遠端規則或插件形成供應鏈風險」，PRD 給的緩解方式是「初期本地優先；未來使用簽名、版本固定和 preview-validate-confirm-apply-audit」，`CLAUDE.md` 也明文要求 AI 設定變更走 preview → validate → confirm → apply → audit。
>
> **v1 硬性限制（含版本鎖，決策已定案 2026-08-22，見第 9 節決策 6：v1 就做）**：
> - 外部 Provider Descriptor 只能是本機檔案，不支援自動遠端拉取/更新。
> - 每個 Descriptor 檔案必須帶 `version` 欄位；載入時對整份檔案內容算一個 content hash，跟本機一個小型信任紀錄（例如 `~/.gtoffice/cache/provider-trust.json`，記錄「這個 provider id 上次使用者確認過的 hash 是什麼」）比對。
> - **首次載入某個 Descriptor，或 hash 跟上次確認的不一樣（代表檔案被改過/版本更新），一律強制先顯示 preview（會跑哪個安裝方式、實際指令內容），使用者手動確認過，才把這個 hash 記為「已確認」並允許真的執行安裝**；hash 沒變就不用每次重新confirm，但安裝前的 preview 畫面固定都要出現，不能靜默安裝。
> - Descriptor schema 額外保留一個 `signature: Option<String>` 欄位，v1 先不強制驗證（因為完整的簽章驗證需要先決定金鑰/信任模型，例如是否要維護一把 GT Office 官方簽章金鑰，這是另一個需要產品/資安決策的題目，不在這次範圍內），但欄位先留著，之後要上簽章驗證不需要再改 schema。這個決定要點是：**version-lock（含 hash 比對與強制 confirm）在 v1 就是真的有效的防護，不是留白**；簽章驗證是預留擴充點，不是本次 v1 的空頭承諾。

這節工程量不小（要動 `agent_installer.rs` 全部的偵測/安裝/解除安裝邏輯），建議**獨立當一個階段做**，而且要先做完，因為第 2 節（外部 Agent 庫）跟第 3 節某些權限類別都會依賴這裡定義出來的 Provider 概念。

**涉及檔案**：`crates/gt-tools/src/agent_installer.rs`（大改）、`crates/gt-agent/src/models.rs`（`normalize_tool_provider_key`、`prompt_file_name_for_tool` 改成查 Provider Descriptor）。

## 6. 終端機渲染破圖 + 未來遊戲化辦公室首頁

### 6.1 渲染破圖

**現況地基**：這個問題已經是專案裡「正在打的仗」，不是沒人發現的新問題。現有已經存在的相關基礎設施：

- `apps/desktop-web/src/features/terminal/station-terminal-render-recovery.ts` — 看名字就是渲染異常後的恢復邏輯
- `station-terminal-renderer-policy.ts` — 渲染器選擇策略
- `station-terminal-replay-drain.ts`、`station-terminal-pending-replay.ts` — 重播佇列處理
- `station-terminal-host-pool.ts` — 終端機 host 的重用池（多個 session 共用 DOM host 時常見的 bug 來源：換 session 沒把舊畫面清乾淨）
- `TerminalDebugPanel.tsx` + 後端 `apps/desktop-tauri/src-tauri/src/terminal_debug/` — 專門的除錯面板與 log
- `docs/xterm-reference.md` — 記錄了目前用 xterm.js 的哪個渲染參考點

**設計方向**：在還沒實際重現、分類破圖情境之前，**不建議直接跳去「換一種渲染模式」**。xterm.js 本身就有 dom / canvas / webgl 三種渲染後端可選，GT Office 現在的選擇跟上面那些 recovery 邏輯是配套調校過的，貿然整套換掉，等於同時要重新驗證所有既有的 recovery 機制還能不能用，風險比預期大。

建議的第一步（可驗證、成本低）：擴充 `TerminalDebugPanel` 的擷取範圍，在破圖發生的當下記錄「目前用的渲染後端、容器尺寸、最近一次 resize 事件、host pool 是否剛發生過 session 切換」，蒐集到幾個實際的破圖 repro 案例後，再决定是修現有渲染器的參數，還是真的要換渲染後端（三選一裡通常 webgl 效能最好但相容性問題也最多，dom 相容性最好但大量輸出時效能差，canvas 是折衷）。**這節建議獨立於其他五節之外，隨時可以平行處理**，不依賴任何其他章節的改動。

### 6.2 遊戲化辦公室首頁（未來項目）

你的原話是「未來會新增」，代表這不是這次改版的即時範圍,但要在**現在**的設計裡留一個接口，不然以後接不上。

核心洞察：這個功能需要的資料，跟第 1 節 agent-canvas 需要的資料，其實是同一份——「這個 workspace 有哪些 Agent、每個 Agent 現在的狀態/活動訊號」。差別只在**呈現方式**：agent-canvas 是節點圖（給要看協作拓樸的人），辦公室首頁是員工小人（給要一眼掃過全局狀態的人）。

設計上建議把「Agent 狀態的即時資料層」跟「怎麼畫」拆開：第 1 節 P0 階段對齊 `AGENT_RUNTIME_UPGRADE_PRD.md` 後產出的那份 Agent 狀態資料層（不管最後是直接借用 PRD 雛形，還是自己做一層通用抽象），應該從一開始就設計成不綁定特定畫面的資料來源，未來的 `features/office-lobby`（新 feature，尚未建立）跟 `features/agent-canvas` 各自訂閱同一份狀態、各畫各的。現在只需要做到「資料層夠通用」，畫面本身留給以後。

## 8. 分階段路線圖

依「小步、可驗證」的專案原則（`CLAUDE.md`），建議順序如下。每個階段結束都要能過 `npm run typecheck` + `cargo check --workspace`，且有明確的驗證方式，不是「看起來對就好」。**本節已依第 9 節的定案決策更新過（2026-08-22）**：因決策 5/7 讓第 2 節範圍大幅縮小、不再依賴 Provider Descriptor 概念，順序做了調整。

| 階段 | 內容 | 為什麼是這個順序 |
|---|---|---|
| P0 | 資料模型地基（皆為 `ADD COLUMN`/`CREATE TABLE`，不接 UI）：`parent_agent_id`、`agent_links` 表、`agent_policy_snapshots` 表、`external_template_path`；**加上 PRD 對齊調研**——動工 P4（agent-canvas）之前，先花一輪對照 `AGENT_RUNTIME_UPGRADE_PRD.md` 的 Runtime Snapshot/Lifecycle State，產出一份簡短結論（agent-canvas 節點狀態要借用 PRD 雛形還是做成通用層），這是決策 4 的具體落地動作 | 後面每一節都要用到，先做完不會被後面的功能卡住 schema；PRD 對齊調研提早做，避免 P4 做完才發現方向錯 |
| P1 | 第 4 節：終端機 New Session 按鈕 | 幾乎純前端、後端已具備能力，是最小可驗證的第一步，用來驗證整個改版節奏 |
| P2 | 第 2 節：Agent 外部範本路徑（決策 5/7 定案後範圍很小：一個欄位 + 一個讀取 command + 建立流程 UI 加一個選項） | 有 P0 的欄位可用；不再依賴 Provider Descriptor（P5），可以提早做，範圍小、風險低 |
| P3 | 第 3 節 Phase A：權限分頁（File System / Shell / Git / Agent / Execution 五類，真的接上執行面） | 有 P0 的表可以用；範圍明確劃在「現有系統掛得上」的五類，不做假權限。**注意**：Agent 類別的 v1 是不依賴 authored edge 的單純開關（見第 3 節註記），P3 在 P4.5 之前做不會產生假權限 |
| P4 | 第 1 節：agent-canvas MVP（先做唯讀的節點圖，畫出現有 Station + 實際 `gto` 派發產生的 derived 連線） | 有 P0 的 `agent_links` 表和 PRD 對齊調研結論；MVP 先不做手畫線和 subagent 建立，降低第一版風險。**驗收標準明確包含**：Agent 即時狀態的資料層要落實 P0 調研的結論（對齊 PRD 雛形，或做成不綁定畫布本身的通用資料層）——不能做完 P4 之後這份資料還是耦合死在畫布的假設裡，否則 6.2 節之後要重拆一次 |
| P4.5 | 第 1 節加強：手畫 authored 連線、畫布上建立 subagent；此時可以把 P3 的 Agent 權限開關升級成依 edge 授權 | 前一步驗證過畫布可用後再加互動 |
| P5 | 第 5 節：Provider Descriptor 重構（`agent_installer.rs` 大改，含決策 6 的版本鎖機制） | 不再是任何其他階段的前置依賴（決策 5/7 讓第 2 節不需要它），但本身風險最高、規模最大（動到最多既有邏輯），建議排在後面、等前面幾個小階段驗證過開發節奏後再啃這塊，且要有 regression test 覆蓋 Claude/Codex 既有行為不能壞掉 |
| 隨時可平行 | 第 6.1 節：終端機渲染破圖除錯 | 獨立問題，不依賴其他階段，也不被其他階段依賴 |
| 未來（本次不排期） | 第 6.2 節：遊戲化辦公室首頁 | 使用者原話是未來項目，只需現在把資料層留通用（見 6.2 設計，且已折入 P4 驗收標準），畫面留待之後 |

## 9. 已拍板決策（2026-08-22）

以下 7 題原本是需要使用者決策的開放問題，已由使用者逐一拍板，內容已同步反映進第 1-8 節。這裡保留決策記錄，方便之後回頭查「為什麼是這樣設計」。

1. **第 1 節連線語意**：兩者都要（authored + derived）。落地方式：derived 先在 P4 做，authored 排到 P4.5。
2. **第 2 節外部路徑是否要跨機器同步**：不用，本機路徑就好。
3. **第 3 節 17 類權限 Phase B 優先順序**：不急，按文件裡判斷的順序開發即可，不需要為特定類別插隊。
4. **第 1 節/第 3 節是否要先跟 `AGENT_RUNTIME_UPGRADE_PRD.md` 對齊**：採方案 (a)——P4（agent-canvas）動工前，P0 階段先花一輪對照 PRD 的 Runtime Snapshot/Lifecycle State 雛形，結論記錄下來再動工，不刻意繞開。
5. **第 2 節 v1 要不要做正式的 Agent Definition/Instance 雙層架構**：不做，採較小的方案（在 `AgentProfile` 加一個 `external_template_path` 欄位）。之後如果實際使用後發現需要範本版本管理、多專案分享等更完整的需求，再另外評估要不要演化成雙層架構。
6. **第 5 節外部 Provider Descriptor 的供應鏈防護要做到什麼程度**：v1 就做版本鎖（content hash 比對 + 檔案有變動時強制 preview/confirm）。完整的簽章驗證因為需要先決定金鑰/信任模型，schema 先保留欄位，不在這次 v1 範圍內做驗證邏輯。
7. **第 2 節跨 workspace 呼叫時，Agent 實例該落在哪個 workspace**：不存在跨 workspace 執行——以使用者原話「我在哪個專案的介面就是在那個，Agent 就應該在那個介面」為準，Agent 一律在使用者目前所在的 workspace 內建立與執行，不新建承接用的 workspace，也不需要 local bridge 做跨 workspace 轉發。
