# 02 後端架構

> 對應目錄：`apps/desktop-tauri/src-tauri/`（Tauri 殼層）+ `crates/`（領域邏輯）

## 1. 後端在做什麼、為什麼需要它

前端（網頁技術）本身不能直接讀寫檔案、開終端機、跑 Git 指令——瀏覽器環境不允許這麼危險的操作。所以這個專案用 Tauri：前端還是網頁，但被包進一個桌面殼層，殼層裡有一個 Rust 寫的後端程式，擁有完整的系統權限。前端要做任何「真正的事」，都要透過固定的管道請後端代勞（見 [03_前後端通訊與多Agent協作機制.md](03_前後端通訊與多Agent協作機制.md)）。

用 Rust 的原因：效能好、跨平台（同一份程式碼編譯出 macOS 和 Windows 版本）、型別安全（編譯期就能抓到很多錯誤）。

## 2. 後端分成兩塊

```
apps/desktop-tauri/src-tauri/   ← Tauri 殼層：只做「入口」和「組裝」
crates/gt-*                     ← 領域邏輯：真正的業務規則在這裡
```

這是刻意的分層，規則寫在 `CLAUDE.md` 裡：

- **不可以**在 Tauri command 入口寫業務邏輯
- 運行時邏輯、編排、helper 要放在 crate 裡
- `app_state.rs` 只負責「把各個 crate 的服務組裝起來」，不承載業務邏輯
- 後端邏輯穩定之後，優先沉澱成獨立的 crate

## 3. Tauri 殼層 (`apps/desktop-tauri/src-tauri/src/`)

| 路徑 | 負責什麼 |
|---|---|
| `commands/` | Tauri command 處理函式，**每個 feature 一個資料夾**，和前端 `features/` 一比一對齊 |
| `app_state.rs` | 全域狀態組裝（把各個 crate 的服務實例組起來，注入到 Tauri 的狀態管理裡） |
| `local_bridge.rs` | 本地 bridge TCP server，給 `gto` CLI 和外部工具用（多 Agent 協作的關鍵，見第 03 章） |
| `channel_adapter_runtime.rs` | 外部 Channel（Telegram/Feishu/WeChat）的 inbound webhook 監聽 |
| `channel_sinks.rs` | 外部 Channel 的 outbound 訊息發送 |
| `connectors/` | 各個外部服務的連接器實作（`connectors/telegram`、`connectors/feishu`、`connectors/wechat`） |
| `daemon_bridge.rs` | 連到 `gt-daemon` sidecar 進程的 client |
| `filesystem_watcher.rs` | workspace 檔案系統變更監聽 |
| `terminal_debug/` | 終端機除錯 log 與診斷 |

`commands/` 底下實際存在的 feature 資料夾：`agent/`、`business_designer/`、`file_explorer/`、`git/`、`keybindings/`、`session/`、`settings/`、`task_center/`、`terminal/`、`tool_adapter/`、`workspace/`。`commands/` 根目錄只放 `mod.rs`（綁定入口）和跨 feature 的 `security.rs`、`system.rs`。

`app_state.rs` 長什麼樣（節錄，可以看到它只是把各個 crate 的型別 `use` 進來、組成一個共享狀態結構，沒有任何業務判斷）：

```rust
use gt_agent_session::SessionRegistry;
use gt_ai_config::StoredAiConfigPreview;
use gt_changefeed::SessionChangeFeed;
use gt_git::GitService;
use gt_session_log::{bind_session_log, SessionLogBinding, ...};
use gt_settings::{EffectiveSettings, JsonSettingsService, RuntimeSettings};
use gt_task::{AgentProviderSessionMetadata, AgentToolKind, TaskService};
use gt_terminal::PtyTerminalProvider;
use gt_workspace::InMemoryWorkspaceService;
```

## 4. 領域 Crates (`crates/gt-*`)

每個 crate 是一個獨立、有明確職責的 Rust 套件，彼此依賴方向是單向往下（不會循環依賴）：

```
                    gt-abstractions   ← 共用 trait 定義，其他 crate 都依賴它
                   ╱     │      ╲
           gt-core   gt-workspace  gt-security
              │          │              │
     ┌────────┼──────────┼──────────────┤
  gt-ai-config  gt-filesystem    gt-terminal-core
     │                         ╱           ╲
  gt-settings          gt-terminal      gt-session-log
     │
  gt-storage → gt-agent → gt-task → gt-git → gt-changefeed → gt-tools → gt-telemetry / gt-keymap

  gt-daemon（獨立的 sidecar 進程，不在主依賴鏈裡）
```

| Crate | 角色 |
|---|---|
| `gt-abstractions` | 共用 trait（`WorkspaceService`、`TerminalProvider`、`GitProvider`、`SettingsStore`、`CommandPolicyEvaluator`）與型別（`WorkspaceId` 等）。所有 domain crate 依賴的是這些 trait，而不是具體實作——這樣才能替換成 mock 做測試。 |
| `gt-core` | 跨多個 crate 用的基礎資料結構 |
| `gt-workspace` | Workspace 生命週期：開啟、關閉、切換、解析 workspace context（根路徑、權限、預設終端機 cwd） |
| `gt-filesystem` | 檔案與目錄操作，強制所有路徑不能跑出 workspace 根目錄 |
| `gt-terminal` / `gt-terminal-core` | PTY session 的建立與管理；`terminal-core` 是終端機模擬引擎（VT parsing、輸出路由、scrollback），`terminal` 是接到 OS 的 PTY provider 實作 |
| `gt-git` | Git 操作：status、diff、history、branch。呼叫 `git` CLI 並解析輸出 |
| `gt-task` | 任務追蹤與生命週期，定義任務派發、批次派發、channel 訊息、Agent runtime 註冊、進度事件——**是目前多 Agent 協作工作流程的核心模型** |
| `gt-agent` | Agent 角色、狀態、安裝流程，定義 `AgentRepository` trait 及其 SQLite 實作 |
| `gt-agent-session` | Agent 對話 session 的發現與恢復（掃描 Claude/Codex 的本地紀錄，串接 SQLite）——詳見 `docs/AGENT_SESSION_ARCHITECTURE.md` |
| `gt-ai-config` | AI provider 設定與憑證管理，走 preview → validate → confirm → apply → audit 流程，憑證存系統 keychain |
| `gt-settings` | 使用者偏好設定，分 user-level / workspace-level / session-level 三層解析 |
| `gt-storage` | SQLite 持久層，提供 repository 實作、schema migration、連線池 |
| `gt-security` | 路徑驗證與 workspace 邊界存取控制 |
| `gt-changefeed` | 即時變更通知，檔案/Git 狀態/設定變化時發事件，前端不用 polling |
| `gt-session-log` | 終端機 session 的 log 記錄，供 replay 與除錯 |
| `gt-telemetry` | 使用量與診斷指標 |
| `gt-keymap` | 快捷鍵設定的資料模型 |
| `gt-tools` | 工具 adapter 與外部連接器基礎設施，定義 Agent tool kind 與安裝器 |
| `gt-daemon` | 獨立的 sidecar 進程，處理重度運算（檔案搜尋、索引），走自訂的 TCP 長度前綴協議，避免拖慢主進程 |

## 5. 為什麼要分這麼多層

`docs/ARCHITECTURE.md` 定義了四層：

```
Presentation（前端 React）
   ↓ invoke + event
Application（Tauri commands）— 只做：驗證輸入、呼叫 domain crate、發事件
   ↓ crate API
Domain（crates/gt-*）— 業務邏輯、領域模型
   ↓ OS / 外部 API
Infrastructure（PTY、檔案系統、SQLite、Git CLI、系統憑證）
```

實務意義：如果你要新增一個功能，**先問「這是規則/邏輯，還是入口/組裝？」**——規則邏輯放進對應的 crate，Tauri command 只做接收請求、呼叫 crate、回傳結果三件事。這樣測試的時候可以直接測 crate（不用啟動整個 Tauri app），而且以後要換掉 UI 或前端框架時，後端邏輯不受影響。

## 6. Mock-first：可測試性

`gt-abstractions` 定義的都是 trait（介面），不是具體實作。例如 `TerminalProvider` 這個 trait 有真的 `PtyTerminalProvider`（實際開 PTY），也可以有測試用的 mock 實作（假裝開了一個終端機，回傳固定內容）。這讓測試不需要真的去開系統終端機、跑真的 Git 指令，跑得快也跑得穩。

新增系統能力（provider）時，要記得同時提供 mock 版本，這是專案的硬性要求。

## 7. 給你的具體建議

如果要改「Agent 建立方式」（例如支援自訂 provider、自訂 prompt 模板），會牽涉到：

1. `crates/gt-agent/` — Agent 的角色、狀態、安裝流程定義在這裡
2. `crates/gt-task/` — 如果新的建立方式牽涉到任務派發模型，這裡是核心
3. `apps/desktop-tauri/src-tauri/src/commands/agent/` — 對應的 Tauri command 入口
4. `apps/desktop-web/src/features/workspace-hub/agent-management-model.ts` — 前端對應的邏輯入口（見 [01_前端架構.md](01_前端架構.md)）
