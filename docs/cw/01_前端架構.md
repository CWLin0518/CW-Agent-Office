# 01 前端架構

> 對應目錄：`apps/desktop-web/`

## 1. 前端在做什麼

前端就是使用者實際看到、操作的畫面：檔案樹、終端機視窗、Git diff、Station 卡片、設定頁面等等。技術上它是一個用 React 寫的網頁應用，被 Tauri 包裝成桌面視窗。前端自己不會直接讀寫檔案、不會直接開終端機——這些「真正做事」的能力都在後端（見 [02_後端架構.md](02_後端架構.md)），前端只負責畫面呈現，以及呼叫後端幫忙做事。

## 2. 技術棧

| 用途 | 技術 |
|---|---|
| UI 框架 | React 19 + TypeScript |
| 建構工具 | Vite |
| 樣式 | SCSS（禁止新增原始 `.css`）+ Tailwind CSS 4 utilities |
| 終端機渲染 | `@xterm/xterm`（把後端傳來的終端機文字畫出來） |
| 程式碼編輯器 | Monaco Editor（VS Code 用的同一套編輯器元件） |
| 拖拉排版 | `@dnd-kit/*`（Station 卡片拖動排列） |
| 動畫 | `motion`（原 Framer Motion） |
| Git 相關 UI | `@git-diff-view/react`、`@gitgraph/react` |
| 虛擬清單 | `@tanstack/react-virtual`（大量列表時只渲染看得到的部分，效能考量） |
| 與後端溝通 | `@tauri-apps/api`（呼叫 Rust 後端 `invoke`、監聽 `event`） |

## 3. 目錄結構

```
apps/desktop-web/src/
├── app/            入口組裝
├── features/       業務 UI，依功能模組分資料夾（重點看這裡）
├── shell/          應用外殼：視窗框架、導航、多語言、平台整合
├── components/     跨 feature 共用元件
├── stores/         真正跨 feature 的全域狀態（目前只有 notification）
├── styles/         design tokens、基礎樣式、工具 class
└── hooks/          共用 React hooks
```

規則（來自 `CLAUDE.md`，寫程式時要遵守）：

- feature 專屬的 UI、hooks、model、樣式都留在自己的 `features/<name>/` 資料夾，不要外流到 `components/` 或 `stores/`
- `components/` 只放**真正跨 feature**共用的元件
- `stores/` 只放**真正跨 feature**的全域狀態；目前只有一個 `notification.ts`，可見這條規則被嚴格執行——大部分狀態應該留在 feature 內部，不要動不動就丟進全域
- `shell/` 只管視窗框架、導航組合、平台整合，不放業務邏輯
- 多語言文字要從元件抽離，不要寫死在 UI 裡（對應 `shell/i18n`）

## 4. Feature 模組清單

`src/features/` 底下每個資料夾對應一個業務功能，且和後端的 `commands/` 目錄一比一對齊（見 [02_後端架構.md](02_後端架構.md) 第 4 節）：

| Feature | 負責什麼 |
|---|---|
| `workspace` | 工作區的開啟、關閉、切換 |
| `workspace-hub` | **多 Station 工作台**：Agent 卡片、拖拉排版、分離視窗——這是你要重新設計「Agent 建立/UI/操作」時最主要會動到的地方 |
| `terminal` | PTY 終端機 session，用 xterm.js 渲染 |
| `file-explorer` / `file-preview` | 檔案樹瀏覽、檔案內容預覽 |
| `git` | Git 狀態、diff、歷史 |
| `task-center` | 任務追蹤與 Agent 派工 |
| `tool-adapter` | 外部 Channel 連接器（Telegram / Feishu / WeChat）的綁定與訊息路由 |
| `session` | Agent 對話 session 的歷史列表、恢復對話 |
| `settings` | 使用者偏好設定、AI provider 設定 |
| `keybindings` | 快捷鍵設定 |
| `change-feed` | 即時變更通知 UI（只吃後端 event，沒有自己的 command） |
| `business-designer` | 需求設計（圖形化、規則、AI 補全） |

## 5. 一個 feature 資料夾實際長什麼樣：以 `workspace-hub` 為例

這是目前專案裡「多 Agent 工作台」的核心 feature，之後你要改 Agent 建立方式、UI、操作機制，大概率會在這裡動刀。它的檔案命名有清楚的分工慣例：

| 檔名模式 | 角色 |
|---|---|
| `*.tsx` | React 元件，例如 `StationCard.tsx`（一張 Station 卡片的畫面）、`WorkbenchCanvas.tsx`（整個工作台畫布） |
| `*.scss` | 對應元件的樣式，例如 `StationCard.scss` |
| `*-model.ts` | 純資料/邏輯定義，不含 UI，例如 `station-model.ts`（Station 的資料結構）、`agent-management-model.ts`（Agent 管理的邏輯） |
| `use*.ts` | React hook，例如 `useStationActivitySignal.ts`（訂閱 Station 活動狀態的 hook） |
| `index.ts` | 這個 feature 對外匯出的入口 |

例如「使用者點擊 Station 卡片上的動作按鈕」這件事，資料流大致是：

```
StationCard.tsx（畫面）
  → station-action-registry.ts（這個動作對應哪個處理函式）
  → station-action-model.ts（動作的資料結構/邏輯）
  → 呼叫 Tauri invoke（見 03 章節）
  → 後端 commands/agent/ 處理
```

## 6. 全域狀態很克制

`stores/` 目錄目前只有 `notification.ts` 一個檔案。這不是還沒補齊，而是刻意的設計：狀態預設留在 feature 內部（用 React state / feature 自己的 model），只有像「全站通知」這種真正跨 feature 共用的東西才會被放進全域 store。你之後設計自己的功能時，也應該先假設狀態屬於某個 feature，而不是預設丟進全域。

## 7. 樣式規則

- 只用 SCSS，不新增原始 `.css` 檔
- 使用響應式單位（`rem`/`%`/`vh` 等），避免直接寫死 `px`
- 樣式分三層：`styles/tokens`（design tokens）、`styles/foundations`（基礎層）、`styles/utilities`（工具 class），feature 自己的樣式則跟著元件放在 `features/<name>/*.scss`
- 需要支援深色/淺色雙主題，不要自行發散出第三種主題
- 新增或調整介面時，要遵循既有設計系統，保持 Apple 風格的一致性

## 8. 給你的具體建議

如果要開始改「UI 呈現方式」，建議的閱讀順序是：

1. `apps/desktop-web/src/features/workspace-hub/WorkbenchCanvas.tsx` — 整個工作台的最外層畫布
2. `apps/desktop-web/src/features/workspace-hub/StationCard.tsx` — 單一 Agent 卡片
3. `apps/desktop-web/src/features/workspace-hub/station-model.ts` — Station 的資料結構，改 UI 前先搞懂資料長什麼樣
4. `apps/desktop-web/src/features/workspace-hub/agent-management-model.ts` — Agent 建立/管理的邏輯入口
