### 1.2 真人實測抓到的追加 bug（不是 code review 找到的）

上述修復完成、code review 過關後，實際請使用者在 GT Office 裡對 `leader` 開新對話測試，**還是沒連到**。追查發現：`leader`／`GMweb_collector`／`Set injector` 這三個 agent 都設定了**自訂 launch command**（例如 `codex --dangerously-bypass-approvals-and-sandbox`），而 `resolve_launch_command()` 原本的設計是「有自訂指令就直接原樣啟動，完全跳過 materialize」——這是刻意的保守設計（怕亂猜怎麼把 `-p <profile>` 插進使用者自己寫的任意字串），但也代表這三個 agent 的 MCP 掛載永遠不會生效。

修復：
- `ResumeService::apply_capability_overlay_to_command()` 改成把 Codex 的 `-p <profile>` 插在**第一個空白字元之前**（也就是程式名稱後面），不是盲目接在字串最後——裸指令 `"codex"` 沒有空白，行為不變；帶自訂旗標的 `"codex --dangerously-bypass..."` 現在會正確變成 `"codex -p <profile> --dangerously-bypass..."`。
- `resolve_launch_command()` 拿掉「有自訂指令就整個跳過」的規則，改成：只要指令的第一個字（不分大小寫）等於這個 tool 的正式程式名稱（`"claude"`/`"codex"`），就照樣跑 materialize + 疊加；不符合的（例如透過 `env` 包起來的指令）維持原樣不動，不亂猜。

修完後請使用者重新對 `leader` 開新對話，直接檢查 `$CODEX_HOME` 底下確認 `gtoffice-9829df7d-...-f31eef32.config.toml` 出現且內容正確（`[mcp_servers.1123]` 含 `command`/`args`），端對端驗證通過。
